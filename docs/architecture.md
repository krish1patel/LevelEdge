# Architecture

LevelEdge is one Python library (`leveledge`) used in three places: a web API that serves the dashboard, scheduled GitHub Actions jobs that forecast and trade, and research scripts that test ideas. This guide describes those components, how data flows between them, and the decisions that shape them.

## Components

```text
┌──────────────────────────────── leveledge (src/leveledge) ────────────────────────────────┐
│  forecaster      sessions · data · features · model · predictor                           │
│  portfolio       portfolio (engine) · live (the traded book) · strategies                 │
│  execution       broker (Alpaca, paper only) · safety (pre-trade checks) · mirror         │
│  market views    outlook (S&P 500 ranges) · regime (GARCH, HAR, HMM, jump models)          │
│  integrity       ledger (hash chain, timestamps, scoring)                                  │
│  market data     kalshi · edge · polygon_data                                              │
└───────────────────────────────────────────────────────────────────────────────────────────┘
        ▲                         ▲                                   ▲
        │                         │                                   │
  app/api.py                 scripts/*.py                       benchmarks/*.py
  (FastAPI, dashboard)       (run by GitHub Actions)            (research studies)
        ▲                         │                                   │
        │                         ▼                                   ▼
  web/ (React, Vercel)     Alpaca paper · Supabase ·          benchmarks/results/*.json
                           `ledger` and `forward-log` branches
```

| Component | Runs on | Purpose |
|---|---|---|
| `src/leveledge` | Everywhere | All modelling, trading and verification logic. Nothing else contains business logic. |
| `app/api.py` | AWS Lambda (and HuggingFace) | A stateless JSON API over the library, with short in-memory caches |
| `web/` | Vercel | The dashboard: Portfolio, Forecaster and Research sections |
| `scripts/` | GitHub Actions | Forward test, paper trading, weekly report, ledger and forward-log jobs |
| `benchmarks/` | A developer's machine | Research studies; their JSON summaries feed the dashboard's Research section |

## Data flows

### Serving a forecast

1. The browser posts a ticker, target time, bar interval and levels to `/api/forecast`. Vercel forwards `/api/*` to the Lambda Function URL.
2. `forecast()` fetches bars from Yahoo Finance, keeps completed regular-session bars, and computes the exact horizon in bars.
3. The model fits once (about 1–3 s) and answers every level from that one fit, so the probabilities stay consistent. An LRU cache reuses the fit for repeated requests.
4. The API returns P(above) for each level, the quantiles, and the out-of-sample record for each level's move.

### Paper trading (weekly)

1. After each weekday close, `paper_trade.yml` runs `scripts/paper_trade.py`. On the last trading day of the week, it computes the book's targets from the latest completed close.
2. It reads the Alpaca paper account and plans whole-share orders that never borrow and skip drift under the 2-point band.
3. `leveledge.safety` runs eight pre-trade checks. Any failure halts the run and posts an alert.
4. Orders queue as day market orders and fill at the next open. `weekly_report.py` posts the results to a GitHub issue.

### Forecast record (daily)

1. `run_forwardtest.yml` forecasts QQQ, SPY, NVDA and TSLA at eight strikes three times a day. It writes the forecasts to Supabase, and it appends them to the public `ledger` branch with an RFC 3161 timestamp.
2. After the close, `ledger_reconcile.yml` appends one score per matured forecast and re-verifies the whole ledger.
3. `forward_log.yml` commits the day's S&P 500 outlook to the `forward-log` branch, and the dashboard scores it as outcomes arrive.

## Storage

| Store | Contents | Mutability |
|---|---|---|
| `ledger` branch (`ledger.jsonl`) | Every live forecast, its timestamps and its score | Append-only, hash-chained, publicly verifiable |
| `forward-log` branch (`outlook.jsonl`) | The daily S&P 500 outlook and the book's targets | Append-only |
| Supabase `forwardtest_logs` | Forward-test rows, with outcomes filled in hourly | Mutable; the ledger is the verifiable copy |
| Alpaca paper account | Positions, orders and fills | Managed by Alpaca |
| `benchmarks/results/` | Research summaries (JSON) | Regenerated by re-running a study |

## Design decisions

- **One distribution, many levels.** The forecaster fits one forecast distribution per ticker, interval and horizon, not one classifier per level. P(above) can't rise with the level, and eight strikes cost one fit.
- **Calibration before cleverness.** The gradient-boosted model keeps a weight only if it beats the volatility baseline on a held-out fold. Class reweighting is banned because it destroys calibration.
- **Pre-declared research.** Every study fixes its rules and pass criteria before it runs, then reads a 2020+ holdout once. A failed idea is published, not tuned.
- **Paper trading, real-account rules.** The paper account trades exactly what a retail cash account can: whole shares, no margin, market orders at the open. This lets the user copy trades into Fidelity.
- **Fail closed.** A failed safety check or a broken ledger stops the job and raises an alert. No job retries its way past a check.
- **Append-only records.** Forecasts and outcomes are never edited in the public record, and scores are new records.
- **Stateless serving.** The API keeps no state beyond caches, so it runs on Lambda, costs nothing while idle, and scales to zero.
